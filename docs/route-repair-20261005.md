# 路线规划结构修复与复验（2026-10-05）

基线：`bd5c818e755c9a95404835b7e3a82d8c3fa2e3a7`。针对报告中的规划失败、错误归因不准确、目标页状态缺失进行修复。

## 根因与证据

原规划提示只列 `steps` 等字段名，没有说明类型、长度等完整要求；应用的 `stageSchema` 却要求 `steps` 为 1–2000 字符的字符串。使用原实现、真实 DeepSeek 和相同阅读总结目标，两次复现 `stages[0..3].steps` 的 `invalid_type`。第二次只采集类型，确认四项实际都是数组，预期为字符串。未将数组转换成字符串或放宽校验。

报告中原先两次失败的日志只保留了 `ZodError` 名称，临时运行目录已清理，无法恢复那两次的逐字段原始结果。这里的字段结论来自本轮原版本复现，证据为 `evidence/route-structural-20261005/baseline.json`。

第二个原因是错误边界抹平了差异：JSON 解析、结构校验、业务约束和调用错误均被提示为检查模型服务。第三个原因是目标页只读目标生命周期，后台任务失败没有进入目标的展示状态。

## 修复结构

- **同一输出契约**：路线、评估、对话、复盘统一注册在 `schemas.js/outputSchemas`。模型提示中的 JSON Schema 直接由实际 Zod 规则生成，返回和事务结算都使用相同验证器。保留严格类型、范围和额外字段限制。
- **安全错误边界**：区分配置、调用、超时、JSON、结构、来源、业务拒绝和中断。`agent_jobs.failure` 持久化错误分类及最多20项字段诊断，包含路径、预期/实际类型、长度和范围，不存失败输出原文、任意对象键、密钥或供应商异常正文。取消后的迟到异常不能改写任务终态或记成新的失败。
- **目标直接展示任务事实**：`planning` 在读取时由持久任务派生，覆盖排队、生成、失败和取消；不复制维护另一套状态。目标卡片和已打开详情都更新，重试清除旧错误，后台最近50条限制不影响目标。旧失败原因缺失时明确说明，保留历史错误，不猜测具体字段。
- **请求归属明确**：结果绑定最新请求、路线版本和阶段。同一目标已有规划时拒绝重复请求；取消/过期结果不能覆盖新草案。调整失败保留已确认路线与证据，新草案仍需用户确认。

数据库迁移002仅新增可空 JSONB 字段，可重复执行。迁移前已备份，用户聚合状态逐项摘要核对无变化。
